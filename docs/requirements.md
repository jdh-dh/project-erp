# 요구사항 분석서 (requirements.md)

## 1. 개요

하드웨어·소프트웨어 개발 프로젝트를 통합 관리하는 웹 기반 ERP 시스템의 요구사항을 정의한다.

- 작성일: 2026-07-07
- 상태: 초안 (사용자 승인 대기)

## 2. 개발 단계 (Phase)

전체 기능을 한 번에 구현하지 않고 아래 단계로 나누어 진행한다.

| Phase | 범위 | 상태 |
|-------|------|------|
| 1 | 기반 구조(인증/사용자), 프로젝트 관리, 고객사 관리 | 완료 (v0.1.0) |
| 2 | 일정 관리 (WBS, 마일스톤, 일정 변경 이력) | 완료 (v0.2.0) |
| 3 | 하드웨어 관리, 소프트웨어 관리 (버전/빌드/배포, GitHub 연동) | 완료 (v0.3.0) |
| 4 | 시험 관리, 이슈 관리, 문서 관리 | 대기 |
| 5 | 릴리즈 이력, 보고서, 프로젝트 비용·자원 | 대기 |

## 3. Phase 1 요구사항

### 3.1 인증 및 사용자 관리

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| REQ-AUTH-001 | 사용자는 이메일과 비밀번호로 로그인할 수 있다. (JWT 발급) | 필수 |
| REQ-AUTH-002 | Access Token 만료 시 Refresh Token으로 재발급할 수 있다. | 필수 |
| REQ-AUTH-003 | 비밀번호는 해시(bcrypt)로 저장한다. 평문 저장 금지. | 필수 |
| REQ-AUTH-004 | 사용자 역할은 admin / manager / member 로 구분한다. | 필수 |
| REQ-AUTH-005 | admin은 사용자를 등록·수정·비활성화할 수 있다. (삭제 대신 비활성화) | 필수 |

### 3.2 고객사 관리

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| REQ-CUST-001 | 고객사를 등록·조회·수정할 수 있다. | 필수 |
| REQ-CUST-002 | 고객사별 담당자(이름, 직책, 연락처, 이메일)를 복수 등록할 수 있다. | 필수 |
| REQ-CUST-003 | 고객사 삭제는 논리 삭제(비활성화)로 처리한다. 프로젝트가 연결된 고객사는 비활성화만 가능하다. | 필수 |

### 3.3 프로젝트 관리

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| REQ-PROJ-001 | 프로젝트를 등록·조회·수정할 수 있다. (코드, 이름, 고객사, 유형, 기간, 설명) | 필수 |
| REQ-PROJ-002 | 프로젝트 유형은 HW / SW / HYBRID 로 구분한다. | 필수 |
| REQ-PROJ-003 | 프로젝트 상태는 준비 → 진행 → 보류 → 완료 → 취소 로 관리한다. | 필수 |
| REQ-PROJ-004 | 프로젝트에 담당자(PM)와 참여 인원을 지정할 수 있다. | 필수 |
| REQ-PROJ-005 | 프로젝트에 계약 정보(계약번호, 금액, 계약일, 기간)를 등록할 수 있다. | 필수 |
| REQ-PROJ-006 | 프로젝트 코드는 중복될 수 없다. | 필수 |

### 3.4 공통 (변경 이력)

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| REQ-COM-001 | 주요 엔티티(프로젝트, 고객사, 계약)의 생성·수정·상태변경은 변경 이력을 남긴다. (누가, 언제, 무엇을) | 필수 |
| REQ-COM-002 | 모든 API는 예외 처리와 로그를 남긴다. | 필수 |
| REQ-COM-003 | 모든 데이터는 프로젝트 중심으로 연결되어 추적 가능해야 한다. | 필수 |

## 3.5 Phase 2 요구사항 — 일정 관리

### 3.5.1 WBS

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| REQ-WBS-001 | 프로젝트별 WBS 항목을 등록·조회·수정할 수 있다. | 필수 |
| REQ-WBS-002 | WBS 항목은 상위 항목(parent)을 지정해 계층 구조를 구성할 수 있다. | 필수 |
| REQ-WBS-003 | WBS 항목은 담당자, 계획 기간(시작일/종료일), 진척률(0~100%), 상태(대기/진행/완료)를 갖는다. | 필수 |
| REQ-WBS-004 | 종료일이 지났는데 완료되지 않은 항목은 '지연'으로 판정한다. (is_delayed 계산 필드) | 필수 |
| REQ-WBS-005 | WBS 항목의 기간 변경은 변경 이력(change_logs)에 기록한다. (일정 변경 이력) | 필수 |
| REQ-WBS-006 | WBS 항목 삭제는 논리 삭제(비활성화)로 처리한다. 하위 항목이 있으면 함께 비활성화한다. | 필수 |
| REQ-WBS-007 | 진척률은 0~100 사이 정수만 허용하며, 100이면 상태를 완료로 처리한다. | 필수 |

### 3.5.2 마일스톤

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| REQ-MS-001 | 프로젝트별 마일스톤(이름, 목표일)을 등록·조회·수정할 수 있다. | 필수 |
| REQ-MS-002 | 마일스톤을 달성 처리할 수 있으며 달성일이 기록된다. | 필수 |
| REQ-MS-003 | 목표일이 지났는데 미달성인 마일스톤은 '지연'으로 판정한다. | 필수 |

### 3.5.3 일정 요약

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| REQ-SCH-001 | 프로젝트 전체 진척률(활성 WBS 항목 진척률 평균)과 지연 항목 수를 조회할 수 있다. | 필수 |

### 3.5.4 권한

- WBS·마일스톤 등록/수정: admin, manager
- 조회: 로그인 사용자 전체
- 담당자(member)는 자신이 담당한 WBS 항목의 진척률·상태를 수정할 수 있다. (REQ-WBS-008)

## 3.6 Phase 3 요구사항 — 하드웨어/소프트웨어 관리

### 3.6.1 하드웨어 관리 (보드/PCB/회로/BOM/부품/제작 이력)

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| REQ-HW-001 | 프로젝트별 보드를 등록·조회·수정할 수 있다. (이름, 리비전, 상태, 설명) | 필수 |
| REQ-HW-002 | 보드 상태는 설계(DESIGN) → 시제(PROTOTYPE) → 양산(PRODUCTION), 단종(OBSOLETE)으로 관리한다. | 필수 |
| REQ-HW-003 | 같은 프로젝트 내 보드는 (이름, 리비전) 조합이 중복될 수 없다. 회로/PCB 변경 시 새 리비전으로 등록한다. | 필수 |
| REQ-HW-004 | 보드별 BOM(부품 목록: 부품명, 부품번호, 제조사, 수량, 위치기호)을 등록·수정할 수 있다. | 필수 |
| REQ-HW-005 | 보드별 제작 이력(제작일, 수량, 제작처, 결과)을 기록할 수 있다. | 필수 |
| REQ-HW-006 | 보드·BOM의 모든 변경은 변경 이력(change_logs)에 기록한다. | 필수 |
| REQ-HW-007 | 삭제는 논리 삭제로 처리한다. 보드 비활성화 시 BOM도 함께 비활성화한다. | 필수 |

### 3.6.2 소프트웨어 관리 (모듈/버전/빌드/배포)

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| REQ-SW-001 | 프로젝트별 SW 모듈을 등록·조회·수정할 수 있다. (이름, 유형, GitHub 저장소 URL, 설명) | 필수 |
| REQ-SW-002 | 모듈 유형은 FIRMWARE / APP / SERVER / LIBRARY 로 구분한다. | 필수 |
| REQ-SW-003 | 같은 프로젝트 내 모듈 이름은 중복될 수 없다. | 필수 |
| REQ-SW-004 | 모듈별 버전을 등록·관리한다. (버전 문자열, 상태: 개발중/릴리즈/중단, 릴리즈일, 변경 내용) | 필수 |
| REQ-SW-005 | 같은 모듈 내 버전 문자열은 중복될 수 없다. 릴리즈 처리 시 릴리즈일이 기록된다. | 필수 |
| REQ-SW-006 | 버전별 빌드 이력(빌드 번호, 커밋 해시, 결과 성공/실패, 비고)을 기록할 수 있다. | 필수 |
| REQ-SW-007 | 버전별 배포 이력(환경: DEV/STAGE/PROD/FIELD, 배포일, 비고)을 기록할 수 있다. | 필수 |
| REQ-SW-008 | GitHub 연동은 1단계로 모듈의 저장소 URL, 빌드의 커밋 해시 기록으로 한다. (API 실연동은 확인 필요) | 필수 |
| REQ-SW-009 | 모듈·버전의 모든 변경은 변경 이력에 기록하고, 삭제는 논리 삭제로 처리한다. | 필수 |

### 3.6.3 권한

- 등록/수정: admin, manager
- 조회: 로그인 사용자 전체

## 4. 비기능 요구사항

- Backend: Python FastAPI, SQLAlchemy, PostgreSQL
- Frontend: React + TypeScript
- 인증: JWT (Access + Refresh)
- 배포: Docker (docker-compose)
- 형상관리: GitHub, 브랜치 전략 main / develop / feature/* / hotfix/* / release/*
